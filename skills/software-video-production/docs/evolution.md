# 从每次制作沉淀 SOP

现状：首例已归档；更新依实际结果和用户反馈。
维护人：当前制作 Agent。
最后更新：2026-10-14。

## 每次收尾

1. 更新 `docs/cases/<日期>-<项目>.md`，链接实际交付和项目记录。
2. 保存用户原话、所指版本、改动、验证范围和接受状态，区分原话与 Agent 归因。
3. 写保留/弃用做法、原因、适用范围、未知。
4. 可复用结论进入对应模块，不把整份聊天塞进 SKILL.md。
5. 实质规则/工具变更更新 `version.json`、roadmap 和入口。没有请求不推送远端或发布技能。

## 经验分级

| 类型 | 如何使用 |
| --- | --- |
| 当次硬约束 | 当前执行；新项目核对是否继续适用 |
| 系列偏好 | 本系列优先，当前明确要求可覆盖 |
| 已验证经验 | 写证据与适用范围，不扩大到所有平台/素材 |
| 试验方向 | 标为待验证，不冒称优秀 SOP |

单个失败不升格为万能禁令。身份片头被否定不等于品牌片永远不能有片头；当前视频像 PPT 不等于 Python/HTML 做视频必然低质。

## 案例模板

```markdown
# 日期 / 项目
现状：交付、待评价或返工；用户实际等级。
维护人：当前制作 Agent。
最后更新：日期。

## 目标与素材事实
平台、观众、功能证据、源时间、约束、素材类型。

## 版本与实际文件
具体改动、最终文件、技术检查和视听检查范围。

## 用户原话
原文与版本；无明确评价就写尚未评价。

## 归因与结论
观察 → 改动 → 结果 → 适用范围 → 未知。

## 下次试验
问题、表达、怎样判断改善、未验证状态。
```

用真实作品验证改进，不看文档是否用了“高级”“电影感”“模型实力”。看钩子、去掉标题后是否讲故事、创意是否服务产品、用户是否仍觉得像低质模板。

某做法再次被否定，修改原规则与归因，不无限堆“必须加特效/角色”的条款。

## 用户要求轻量归档

用户明确只保留成片/封面、删除工程时按当次范围清理；先核对保留文件、哈希和绝对路径边界，轻量复盘保存评分、原话、来源与验证摘要。不得为了完整工程习惯留下原画包、缓存和大ZIP，也不因将来可能重建重复询问已授权的删除。原始共享素材库、其他项目不属于当前工程。

清理后同步入口与案例：不再链接已删除的字幕、时间轴、工程或QA图；注明本地无法完整重建。发布状态区分用户确认与Agent独立检查，不能从“已发布”推导播放或留存表现。
